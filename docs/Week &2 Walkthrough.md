**Week 2 Walkthrough — Task Tracker AWS Deployment**

Overview

During Week 2, I deployed the Task Tracker application to AWS manually using the AWS Management Console. The purpose of this exercise was to understand what each AWS resource does and how the different resources connect together before rebuilding the same infrastructure with Terraform in Week 3.

The application was first tested locally using Docker and then deployed to AWS using Amazon ECR, Amazon ECS/Fargate, CloudWatch, an Application Load Balancer, a target group, and two security groups.

The application was eventually accessible through the Application Load Balancer.

**1. Local Docker Setup**

Before deploying to AWS, I ran the application locally using Docker.

The application was started with:

docker compose up --build

The application listened on port 8080, and I accessed it through:

http://localhost:8080

The application loaded successfully and showed the Task Tracker page with the initial tasks.

Problems encountered

The main issue during the local setup was with Docker and the Windows Subsystem for Linux (WSL).

Docker was not initially working because the WSL component/version on Windows needed updating. I resolved this by removing the WSL feature and then updating WSL using:

wsl --update

After the WSL update was completed, Docker was able to run successfully without further problems.

This was useful because it showed that Docker depends on the underlying virtualization/WSL environment being correctly configured on Windows.

**2. Understanding Docker Storage**

I also tested the difference between:

docker compose down

and:

docker compose down -v

docker compose down removes the containers but keeps the Docker volume and its data.

docker compose down -v removes the containers as well as the volume, which means the stored application data is deleted.

The Task Tracker application currently stores its data in a SQLite database inside the Docker storage volume.

To make the data survive container deletion, the database would need to be stored using persistent storage, such as a mounted persistent volume or an external database.

**9. Application Load Balancer**

Resource created

Application Load Balancer (ALB)

Name

task-tracker-alb

Scheme

Internet-facing

IP address type

IPv4

Network

The load balancer was placed in the default VPC using at least two availability zones.

Listener

Protocol: HTTP

Port: 80

The listener forwards incoming traffic to:

task-tracker-tg

Purpose

The load balancer provides the public entry point to the application.

The ECS/Fargate task has a private IP address that can change when the task restarts. The load balancer provides a stable public endpoint and forwards requests to healthy ECS tasks.

It also performs health checks against: /health

If the task stops responding correctly, the load balancer can remove it from service.

**10. Security Group 1 — ALB Security Group**

Resource created

alb-sg

Rule

Inbound

Protocol: HTTP/TCP

Port: 80

Source: 0.0.0.0/0

Purpose

This security group protects the Application Load Balancer.

Port 80 is open to the internet because the ALB is the public front door of the application.

Users therefore connect to the ALB rather than directly to the ECS task.

\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_\_

**11. Security Group 2 — Application Security Group**

Resource created

app-sg

Rule

Inbound

Protocol: TCP

Port: 8080

Source: alb-sg

The important part of this rule is that the source is the security group alb-sg, not an IP range such as 0.0.0.0/0.

Why the application security group points to the ALB security group

The purpose is to make sure that only traffic coming through the Application Load Balancer can reach the application on port 8080.

The traffic flow is therefore:

Internet

&#x20;  |

&#x20;  | HTTP :80

&#x20;  v

ALB

(alb-sg)

&#x20;  |

&#x20;  | TCP :8080

&#x20;  v

ECS/Fargate Task

(app-sg)

Using alb-sg as the source means the application only accepts traffic from resources associated with that security group.

If I had used:

0.0.0.0/0

for port 8080, the ECS task could potentially be reached directly from the internet, bypassing the load balancer.

This would defeat the intended network design.

The assignment specifically warns that the application security group should allow the load balancer to reach the task, rather than opening port 8080 to everyone.

**14. Scaling Test**

I tested the application with one and then two ECS tasks.

The initial desired task count was: 1

I temporarily changed it to: 2

After both tasks became healthy, the load balancer distributed requests between the two task instances.

The application displays a served by value, which identifies the container instance serving the request.

When two tasks were running, the served by value could change between the two task IDs as requests were distributed between them.

The request counters could also differ because each task maintains its own counters.

After testing, the desired task count was returned to: 1

This demonstrated horizontal scaling using ECS/Fargate and the Application Load Balancer.

**Problem 3 — Security group connectivity**

The application security group needed to allow traffic from the load balancer.

The correct rule was:

Port: 8080

Source: alb-sg

This allows the ALB to communicate with the ECS task while preventing direct internet access to the application port.

The important lesson was that the source should be the load balancer's security group rather than an IP range.

**18. Teardown**

At the end of the exercise, the infrastructure was removed to prevent unnecessary AWS charges.

The resources were deleted in the required order:

1\.	Set ECS desired tasks to 0.

2\.	Waited for the task to stop.

3\.	Deleted the ECS service.

4\.	Deleted the Application Load Balancer.

5\.	Deleted the target group.

6\.	Deleted the ECS cluster.

The ECR repository, CloudWatch log group, and task definition were left because they cost very little and may be required for subsequent work.

The purpose of the teardown was also to demonstrate an important cloud-management practice: resources should not be left running when they are no longer required.

**19. Key Lessons**

The main things I learned from this deployment were:

1\.	A Docker image is the packaged application, while a container is a running instance of that image.

2\.	ECR provides AWS with a location from which it can pull the container image.

3\.	An ECS task definition describes how the container should run.

4\.	An ECS service keeps the required number of tasks running.

5\.	Fargate allows the container to run without managing EC2 servers.

6\.	The Application Load Balancer provides the public entry point to the application.

7\.	The target group connects the load balancer to the ECS task.

8\.	The ALB security group allows public HTTP traffic on port 80.

9\.	The application security group allows port 8080 only from the ALB security group.

10\.	Security-group-to-security-group rules are preferable here to opening the application port to the entire internet.

11\.	CloudWatch stores the application logs.

12\.	The /health endpoint allows the load balancer to determine whether the application is healthy.

13\.	Scaling from one task to two demonstrated horizontal scaling.

14\.	Cost monitoring and teardown are important because cloud resources can continue generating charges even when the application is not being actively used.

15\.	The manual deployment provides the information needed to recreate the infrastructure using Terraform in Week 3.
